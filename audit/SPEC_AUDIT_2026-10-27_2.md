The first audit's 37 findings all stand. 33 are confirmed as written; 4 are confirmed with a correction that changes the proposed resolution (F01, F12, F14, F35). This audit adds **19 new findings: 3 High, 7 Medium, 9 Low**, almost all of them kernel facts the specification gets wrong or does not know, and each one was verified in the kernel source and, where a container can show it, reproduced on the running kernel; the last two are a host-portability requirement (N18) and a forthcoming configuration change (N19) the maintainer announced during the audit.

Three results change the design space rather than a sentence:

1. **The kernel accepts a tunnel on a socket that is bound but never connected** (N03, K15). Sessions and their interfaces exist, every frame sent into them is dropped by the kernel's own transmit check, and nothing leaves any device. The specification's premise that "a connected L2TP/IP socket needs a peer and a route" (A19) is false, so the discard addresses, the null device, the grace period and route repair are a choice, not a necessity. **The maintainer decided during the audit to take this path** and to drop the discard routes, the null device and their monitoring, on two conditions that were then verified: the property holds on every release from v6.8 to v7.3 regardless of configuration, and such a socket can be connected later (K16). The decision and the precise kernel requirements it rests on are in their own section below.
2. **The discard-address design rests on kernel behaviour it does not have.** IPv4 discard routes vanish silently when the null device goes down or away (N01, K7); frames of a discard-connected tunnel follow the routing table at transmit time, not at connect time (N02, K3b); a socket bound to an ordinary device can never use a null-device route and, for IPv4, connects to anything on-link and sends ARP out of the device (N06, K2b/K3).
3. **Two kernel constraints the specification must state.** `IPV6_V6ONLY` is fixed at socket creation for L2TP/IPv6 sockets, so the first audit's proposed fix for `bindv6only=1` hosts is impossible (N04, K1); and a peer change by a plain `connect()` keeps the previous source address, misreports it, and fails with `EAFNOSUPPORT` from an IPv4-mapped peer to an IPv6 peer (N05, K12).

The maintainer's three notes given during the audit (listen for null-device down events; prefer IPv6 discard routes where IPv6 is not disabled; assign `fe80::1/64` to the null device when no link-local is generated) are each confirmed by an experiment and recorded under N01, N09 and N08 with the kernel facts that bound them. No code was changed.

### F01 — corrected

The first audit read `sock_bindtoindex_locked` correctly: `CAP_NET_RAW` is checked only when `sk_bound_dev_if` is already set (`sock.c:634-636`). K2, run in a container with `NET_RAW` dropped, shows the full picture: the first `SO_BINDTODEVICE` succeeds; a second one to another device, or clearing the binding, fails `EPERM`; a `connect(AF_UNSPEC)` clears the binding (`udp.c:2009`), after which binding to another device succeeds again; `SO_BINDTOIFINDEX` behaves identically. Consequences for the specification:

- R4 and H15 are wrong in one direction: binding at tunnel creation never needs `CAP_NET_RAW`, and the reconnect sequence T19 prescribes (disconnect, rebind, connect) never does either, because the disconnect clears the binding first.
- They are wrong in the other direction too: T11 and T12 ("the socket is rebound to the latter", "rebound likewise") describe rebinding a socket that is still bound, which is exactly the operation that needs `CAP_NET_RAW`. If the daemon always disconnects before it rebinds, the capability is never needed and G10 can drop it; if it rebinds in place, R4 must say that the capability is needed for *changes* of a binding, not for having one.
- The traffic-safety contradiction between G5 and R4/H15 (a bound configuration sending through another device after a failed bind) stands, and N03 offers a resolution that needs no capability at all: a bound socket that is never connected sends nothing.

### F12 — corrected

K1 reproduces the refusal: with `net.ipv6.bindv6only=1`, `socket(AF_INET6, SOCK_DGRAM, 115)` succeeds, `bind` succeeds and `connect(::ffff:192.0.0.8)` fails `ENETUNREACH` (`datagram.c:188-191`). The first audit proposed clearing `IPV6_V6ONLY` on each socket. That is impossible on an L2TP/IPv6 socket: `l2tp_ip6_open` sets `inet_num = IPPROTO_L2TP` to prevent autobind (`l2tp_ip6.c:228-233`), and `IPV6_V6ONLY` refuses with `EINVAL` whenever `inet_num` is set (`ipv6_sockglue.c:656-659`), before and after `bind` (K1 shows both). The value is fixed from the sysctl at creation (`af_inet6.c:228`). What remains possible is recorded as N04: read the value back with `getsockopt(IPV6_V6ONLY)` (the getter is unconditional, `ipv6_sockglue.c:1212-1214`) and use `AF_INET` sockets for IPv4 peers on such hosts, or declare `bindv6only=0` a host requirement that the daemon checks at start-up.

### F14 — corrected

The first audit cited the on-link fallback as a possibility. K2b and K3 show its actual shape, and it is worse than described:

- A socket bound to an ordinary device with no route at all to `192.0.0.8` connects successfully (`route.c:2789-2813`), takes the device's address as source, and, when the device has no address, an address of *another* device (K3: `bind=o1` connected with `local=10.1.1.1`, the address of `d0`). Sending then emits `ARP who-has 192.0.0.8` on the device (K3, captured on the veth peer). For IPv6 the same socket fails `ENETUNREACH`.
- A socket bound to an ordinary device that is a VRF member is routed in the VRF's table (`l3mdev.c:280-281`), not the main table as D4 says, and a lookup with an output interface matches only routes through that interface (`fib_trie.c:1419`): a null-device route in the VRF's table does not help it either (K2b: `bind=s0` fails `EHOSTUNREACH` whether the route is in the main table or in table 40, while `bind=vrfA` succeeds).

So a tunnel bound to an ordinary device can never be connected to a discard address through a null device, and for IPv4 it cannot even be prevented from connecting. N06 states the resulting specification error; N03 gives the resolution that removes the need for a route.

### F35 — corrected

K10 settles what the first audit left to an experiment. With an 8 KiB receive buffer, a burst of 300 link creations, and a lookup sent after the burst: the next `recv` returns `ENOBUFS` immediately (`netlink_overrun`, `af_netlink.c:352-357`, reported through `sock_error` in `datagram.c:251-254`); the queued broadcasts that did fit are then readable; the lookup's reply never arrives (dropped at `af_netlink.c:1229-1235`); after the queue is drained a new lookup is answered. With `NETLINK_NO_ENOBUFS` the error disappears and only the loss remains, and in that run the reply was dropped while its 52-byte **ack arrived**: a lookup can "succeed" with an ack and no data. E21's "times out rather than failing" and the same sentence in `docs/testing.md` lines 100-101 describe one configuration (`NETLINK_NO_ENOBUFS` set, or the error consumed by another read) and not the kernel contract. A filter attached to the socket drops its own unicast replies too (K10c, `af_netlink.c:1347-1352`), which E20's "seeds it from the kernel" must take into account (N12).

### N01 — Discard routes disappear without any event the specification watches

**Severity: High. Type: Missing trigger; kernel-confirmed.**

**Evidence:** [D11–D12](../docs/spec/discard.md#repair), lines 82-95; [E9](../docs/spec/events.md#route-events), lines 65-72; [E3–E4](../docs/spec/events.md#link-events), lines 27-38; [R32–R33](../docs/spec/requirements.md#other-network-managers), lines 69-70; [H7](../docs/spec/hosts.md#vrfs), lines 46-53; convergence bound "A discard route the daemon installed is removed", [promises](../docs/spec/promises.md#convergence-bounds) line 63. Kernel: KF10, KF23. Experiment: K7.

D11 repairs a route "the daemon watches for the removal of", E9 says that "a discard route is removed" is the only route event the daemon acts on, and E3/E4 say nothing about the null device. K7 shows what the kernel actually reports when an owned null device carrying `192.0.0.8/32` and `100::/128` in the main table and in a VRF table is handled by another manager:

| Action | `RTM_DELROUTE` for `100::` | `RTM_DELROUTE` for `192.0.0.8` | Routes afterwards |
|---|---|---|---|
| null device set down | yes, both tables | **none** | all four gone |
| null device set up again | — | — | none restored |
| VRF deleted | **none** | **none** | both routes still in the old table |
| VRF recreated with another table | — | — | new table empty |
| null device deleted | yes, both tables | **none** | all gone |

IPv4 routes dropped with their device are flushed without notification (`fib_trie.c:2074-2076` notifies only routes removed with their preferred source). So on an IPv4 tunnel, or on any host where only the IPv4 discard route exists (H3's `disable_ipv6` hosts, or an `AF_INET` host), a null device that another manager brings down or deletes leaves the discard address unrouted and the specification has no event, no timer and no retry that notices: D12 forbids repair from creating a route that was not observed removed, E13 runs only for a *pending real* peer, and T18 excludes address events. On a dual-stack host the IPv6 removal is notified, so the repair runs, but only because both routes happened to be installed. A VRF replaced with a new table (H7, R32 promise "its discard route moved to the new table") produces no route event at all: the old table keeps the routes and the new one has none, so the tunnel's next connect to the discard address fails and nothing installs the route, because D6's installation path is described as part of creation, not of reconnection. Bringing the device up again restores nothing. The maintainer's note during this audit ("we might also need to listen for device down events for `rsl2tpnullX`") is exactly the missing trigger.

**Resolution:** Make the owned null devices and the configured VRF names part of the link events the daemon handles: an owned null device seen down, deleted or moved, and a VRF device appearing or being replaced, each trigger the same repair as a route removal (re-check every owned route with a route lookup, reinstall or recreate). Define table migration explicitly: whether routes left in a retired VRF table are removed (they are the daemon's) or abandoned, and when. State that routes are never restored by the kernel after a down/up cycle. Alternatively adopt N03, which removes the routes and the device altogether.

**Validation:** K7 (`k_iponly.sh`), and the same with a VRF-bound tunnel connected to the discard address while the VRF is replaced.

### N02 — Frames of a discard-connected tunnel follow the routing table at transmit time, not at connect time

**Severity: High. Type: Incorrect kernel model; traffic-safety guarantee not maintained.**

**Evidence:** [G5](../docs/spec/promises.md#unconditional-promises), line 19; [D3](../docs/spec/discard.md#addresses), lines 25-33; [D6](../docs/spec/discard.md#routes), lines 48-53; [C10](../docs/spec/configuration.md#start-up), line 78 ("where frames are dropped"); [T18](../docs/spec/tunnels.md#peers-that-cannot-be-reached), lines 141-143; [E9](../docs/spec/events.md#route-events), lines 65-72 ("route additions ... are not watched"); [R20](../docs/spec/requirements.md#the-operator), line 44. Kernel: KF9. Experiment: K3b.

The specification treats a connect to a discard address as fixing where frames go. The kernel fixes the source address at connect and nothing else: every transmit re-looks up the route when the cached one is stale, and every IPv4 route change makes it stale (`ip_output.c:496-505`, `fib_trie.c:1322`, `1385`, `1756`; IPv6 `inet6_connection_sock.c:104-110`). K3b connected sockets of both families to the discard addresses through a null-device route, replaced that route by one via a veth, and captured on the veth peer an L2TP/IPv6 packet `2001:db8:1::1 → 100::` and, for IPv4, the ARP resolution of the new gateway from the source fixed at connect time. No event reaches the daemon: E9 drops every route addition and replacement in the kernel, and T18 forbids reconnecting a discard-connected tunnel on address events.

The consequence is that G5's "frames of a tunnel without a peer never leave the host unless the operator routed the discard address out" is true only at the moment of the connect. D6 makes it worse by preferring the host's own route when one exists: a discard-connected tunnel then depends on whatever that route becomes. R20 puts the burden on the operator but gives the daemon no way to notice that the burden was not met.

**Resolution:** Either state the guarantee honestly (frames are dropped while the sink route is the one selected for the discard address, which the daemon does not monitor), or make it hold: watch additions and replacements of routes covering the discard prefixes in every table (the filter already parses the destination to pass removals), and re-verify the sink after each; or bind every discard-connected unbound tunnel to the null device, so that no route change can redirect its frames (IPv4 then stays on the device even without a route, by the on-link rule of KF8; IPv6 still needs the host route through that device); or adopt N03, under which a tunnel without a peer sends nothing whatever the routing table says.

**Validation:** K3b (`k_probe.sh`), both families, with and without a bound device.

### N03 — The kernel accepts a tunnel on an unconnected socket, which is the sink the specification is looking for

**Severity: High (design premise). Type: False premise with a simpler, safer alternative.**

**Evidence:** [A19](../docs/spec/architecture.md#why-this-shape), lines 159-162; [discard introduction](../docs/spec/discard.md), lines 5-8; [T1](../docs/spec/tunnels.md#the-right-state-of-a-tunnel) "Connected", lines 22-23; [T16](../docs/spec/tunnels.md#peers-that-cannot-be-reached), lines 127-135; [T20](../docs/spec/tunnels.md#source-addresses), lines 160-166; [M7](../docs/spec/model.md#the-degradation-ladder) step 3, lines 75-78; [P6](../docs/spec/process.md#readiness), lines 36-40. Kernel: KF14. Experiments: K15a–K15c.

A19 says "a connected L2TP/IP socket needs a peer and a route; the discard addresses are the only peers that are always correct to send to and never answer", and the whole of the discard page follows from it. The kernel does not require the socket to be connected. `l2tp_validate_socket` checks the namespace, the type, the family, the protocol and that the socket is unused (`l2tp_core.c:1467-1487`); the only place the connection state matters is the transmit path, which drops every frame of a user-space-socket tunnel whose socket is not established (`l2tp_core.c:1086-1090`). K15 did, on the running kernel, what the daemon would do minus the connect: an `AF_INET6` L2TP/IP socket bound to `::` with a connection id, `L2TP_CMD_TUNNEL_CREATE` with that descriptor, `L2TP_CMD_SESSION_CREATE` with an Ethernet pseudowire and a name. Both succeeded; the device existed and came up; `ip l2tp show tunnel` reported `From :: to ::`; the kernel's own router solicitation and MLD reports on the fresh device were counted as `tx_dropped` before any frame was injected; two injected frames were dropped; after a `connect` a frame was transmitted; after a disconnect the next one was dropped; closing the socket removed the tunnel, the session and the device. The same held for an `AF_INET` socket (K15c) and for a socket bound to a device with `SO_BINDTODEVICE` and never connected, during which nothing left that device (K15b, captured). The specification already contains the state: T20 records a tunnel as "disconnected" after a failed reconnect.

The consequence is not a defect in a sentence but in the premise: the discard addresses, the per-family fallback (D2), the null device and its name space (D7, D9, D10, R19), the grace period (D6, E15, G15's ten seconds), route installation and repair (D8, D11, D12, E9, E16), the route-churn filter's reason for existing (A18, E9), and the kernel facts that break them (N01, N02, N06, N08, N09, F05, F06, F14, F15) are all consequences of requiring a successful connect for a tunnel that has nothing to send to. A tunnel without a peer that is simply not connected keeps every promise the discard address was meant to keep, and keeps them unconditionally: nothing leaves the host, no route is involved, no device is created, no capability is needed, readiness (P6: the tunnel and the session exist) is reached as soon as the kernel has created them, and a peer that becomes reachable is applied by one connect.

**Resolution:** Replace A19 and the discard page's premise: the right state of a tunnel without a reachable peer is *disconnected*, with the binding applied and the sessions created; "connected to a discard address" becomes at most an optional, observability-motivated variant. Rewrite T1's "Connected", T16/T17/T20, M7's ladder (step 3 becomes "disconnected"), D1–D13 (retire, or keep as the optional variant with N01/N02/N06/N08/N09 resolved), E13/E15/E16, H2–H6, and the readiness bounds in G15 (no ten-second grace). Keep the discard address only where an operator-visible peer in `ip l2tp show tunnel` is wanted, and then say what it costs. Note the kernel quirk N14 for the disconnected state's appearance in the kernel record.

**Validation:** K15 (`k_unconn.sh`); then the daemon's interop matrix with the change, which this audit did not run because it changes code.

### N04 — `IPV6_V6ONLY` is fixed at creation on L2TP/IPv6 sockets; `bindv6only=1` hosts need a different rule

**Severity: Medium. Type: Infeasible resolution of F12; missing host rule.**

**Evidence:** [T3–T5](../docs/spec/tunnels.md#address-families), lines 32-50; [H1–H4](../docs/spec/hosts.md#address-families), lines 11-32; [R1](../docs/spec/requirements.md#the-host), line 17. Kernel: KF7. Experiment: K1.

The refusal that F12 predicted is reproduced (K1: `connect(::ffff:192.0.0.8)` fails `ENETUNREACH` with `bindv6only=1`). The remedy the first audit proposed, clearing `IPV6_V6ONLY` on each socket, fails `EINVAL` before and after `bind` because `l2tp_ip6_open` pins `inet_num` (`l2tp_ip6.c:231`) and the option refuses whenever it is set (`ipv6_sockglue.c:656-659`). With `bindv6only=0` the same socket connects to the mapped address and reports `::ffff:10.1.1.1` as source.

**Resolution:** T4's "when, and only when, the kernel refuses an `AF_INET6` L2TP/IP socket" must gain a second case: when a freshly created `AF_INET6` socket reports `IPV6_V6ONLY=1` through `getsockopt` (always readable, `ipv6_sockglue.c:1212-1214`), IPv4 peers need `AF_INET` sockets on this host, and the property of T3 that a peer can move between families on one socket does not hold; the specification must say which tunnels get which socket (the configured `ip_version` decides, and a host-name tunnel whose answers change family needs a re-creation on such hosts). Or add the host requirement `net.ipv6.bindv6only=0`, checked at start-up and reported as a host defect, which is simpler and matches R1's spirit. Either way the check must happen before the first connect, because the errno of the refusal (`ENETUNREACH`) is one T16 classifies as transient, and the daemon would otherwise sit on the discard address retrying every second forever.

The maintainer's note that the daemon could set `net.ipv6.bindv6only=0` itself, with documentation, is a third option with three consequences the specification would have to carry. The sysctl is per network namespace (`net->ipv6.sysctl.bindv6only` is initialised per namespace, `af_inet6.c:955`; K1 set it inside a container without affecting the host), so the daemon would change the default for every `AF_INET6` socket of the namespace it runs in, which in the initial namespace is every program on the host: that is a host policy change the operator must be told about, and the Linux default is already 0, so a host with 1 chose it. G10's "changes no global kernel setting" and P21's "no access to ... kernel tunables" (which the shipped unit enforces with `ProtectKernelTunables`) both forbid it today. The maintainer's decision during the audit is a configuration option that permits namespace-changing operations of this kind: with it off, the daemon only checks and reports (and applies the `AF_INET` rule above); with it on, the daemon writes the tunable in its own namespace at start-up, G10 and P21 carry a documented exception scoped to that option, and the shipped unit must either drop `ProtectKernelTunables` or, on systemd hosts only, be paired with a `sysctl.d` fragment that makes the write unnecessary; on other init systems the daemon-side write is the only mechanism (N18). The maintainer further judged an opt-out default acceptable, on two grounds the evidence supports: the write happens only when the value is 1, which is not the Linux default, and a value of 1 left in place makes every IPv4 peer on an `AF_INET6` socket permanently unreachable with an errno (`ENETUNREACH`, K1) that the specification treats as transient, so the damage is silent and lasting. The specification should then say three things plainly: that the daemon changes a namespace-wide default for every program in its namespace when it finds it set, that the change is logged at warning level with the old value, and that the option turns it off for hosts where 1 was a deliberate hardening choice.

The maintainer also set the scope of the authorization: when the option is on, the daemon keeps the value at zero for its whole lifetime, re-asserting it whenever a flip to 1 is detected, not only at start-up. That is a deliberate exception to the specification's rule of never fighting another manager (S12's reasoning that two managers re-asserting never converge), justified because the other value breaks the daemon's own sockets; the specification should state the exception and its reason. The kernel gives no notification for a sysctl change and procfs files do not support inotify, so detection is by the per-socket check: a freshly created `AF_INET6` socket that reports `IPV6_V6ONLY=1` is the evidence of a flip, after which the daemon writes 0 again, logs it, discards that socket and creates a new one; sockets created before the flip are unaffected because the value is copied at creation (`af_inet6.c:228`). A scratch-socket check at every reconcile makes the detection independent of tunnel creations. Whatever the default, the per-socket check above stays, because the sysctl can be changed after the daemon started and nothing notifies it.

**Validation:** K1 (`k_probe.sh`).

### N05 — A peer change "in place" keeps the old source unless the socket is disconnected first

**Severity: Medium. Type: Ambiguous operation with a kernel-confirmed wrong default.**

**Evidence:** [T1](../docs/spec/tunnels.md#the-right-state-of-a-tunnel) "Source", lines 19-21; [T15](../docs/spec/tunnels.md#peers), lines 118-123 ("applied as a peer change in place ... on the same socket"); [T17](../docs/spec/tunnels.md#peers-that-cannot-be-reached), lines 137-139; [T19](../docs/spec/tunnels.md#source-addresses), lines 147-158; [E10](../docs/spec/events.md#dns-events), lines 76-82 ("moved to the new address in place"); [E7](../docs/spec/events.md#address-events), lines 52-56; [D13](../docs/spec/discard.md#leaving-the-discard-address), lines 99-103. Kernel: KF13. Experiment: K12.

T19 defines a reconnect as disconnect, rebind, connect, but only for source-triggered events; peer changes (T15, T17, E10) are "applied in place" without saying whether the socket is disconnected first. The kernel makes the difference material. K12, on sockets connected to a peer reachable through one device and then connected directly to a peer reachable through another: the source stayed the first device's address, for IPv4, for IPv6 and for IPv4-mapped peers alike (`ipv4/datagram.c:38-39`, `64-65`; `ipv6/datagram.c:51`). From an IPv4-mapped peer to a native IPv6 peer the direct connect failed `EAFNOSUPPORT` (`ip6_output.c:1215-1219`), an errno T16 does not know. From a native IPv6 peer to an IPv4-mapped one it succeeded but `getsockname` kept reporting the IPv6 source while the IPv4 source actually used was another address (`ipv6/datagram.c:206-208` only sets the mapped source when the IPv6 one is empty), so E7's "the daemon identifies the source by asking its own socket" would be answered wrongly. A `connect(AF_UNSPEC)` before each connect gave the right source and the right family every time (`udp.c:2010-2011`).

**Resolution:** Define one reconnect operation (disconnect; apply the configured binding; connect) and require it for every peer change, including DNS answer changes, leaving a discard address or the disconnected state, and family changes. State that a direct connect without a disconnect is a defect, that `EAFNOSUPPORT` from a connect indicates that defect, and that a source read back from the socket is meaningful only after such a reconnect.

**Validation:** K12 (`k_reconn.sh`).

### N06 — A tunnel bound to an ordinary device has no local sink, and its routing context is not the main table

**Severity: Medium. Type: Incorrect routing model; kernel-confirmed. Extends F14.**

**Evidence:** [D4](../docs/spec/discard.md#routes), lines 37-41; [D8](../docs/spec/discard.md#the-null-device), lines 64-68; [T13](../docs/spec/tunnels.md#bind-devices), lines 97-102; [H7](../docs/spec/hosts.md#vrfs), lines 46-53; [D3](../docs/spec/discard.md#addresses), lines 29-33. Kernel: KF8. Experiments: K2b, K3.

D4 says a socket "bound to an ordinary device" uses the main table and D8 installs the discard route "in the main table or in the VRF's table" through the null device. For a socket bound to an ordinary device the kernel matches only routes whose output device is that device (`fib_trie.c:1419`), so a route through the null device never applies to it, in any table (K2b: `bind=s0` fails with the route in the main table and with the route in the VRF table; only `bind=vrfA` succeeds). If the device is a VRF member the lookup is redirected to the VRF's table (`l3mdev.c:280-281`), not the main one. And for IPv4, when the lookup fails, the kernel assumes the destination is on-link and connects anyway (`route.c:2789-2813`): K3 connected a socket bound to a device with no route to `192.0.0.8`, with the device's address as source, or with another device's address when the bound device had none, and sending produced `ARP who-has 192.0.0.8` on the wire. For IPv6 the same socket fails `ENETUNREACH`.

So T13's "sits on a discard address until a device of the configured name exists" and D3's "MUST NOT leave" cannot both be met by a device-bound tunnel: the IPv6 discard address is unreachable for it, and the IPv4 one is "reachable" in a state that emits ARP requests through the device the operator configured for the real peer.

**Resolution:** Under N03, a bound tunnel without a reachable peer stays disconnected, which needs no route and sends nothing. If discard addresses are kept, D4 must describe the routing context as the one the kernel selects for the socket's bound device (the device's L3 domain, and only routes through that device), and T13 must say that a device-bound tunnel is not connected to a discard address at all.

**Validation:** K2b and K3 (`k_probe.sh`).

### N07 — The errno catalogue of T16 is wrong, and link-local peers rebind the socket

**Severity: Medium. Type: Incorrect failure classification; missing grammar.**

**Evidence:** [T16](../docs/spec/tunnels.md#peers-that-cannot-be-reached), lines 127-135; [M13](../docs/spec/model.md#failure-classes), lines 121-137; [C7](../docs/spec/configuration.md#tunnel-entries) `remote_addr`, line 51; [H3](../docs/spec/hosts.md#address-families), lines 22-27; [T11](../docs/spec/tunnels.md#bind-devices), lines 83-89; [T21](../docs/spec/tunnels.md#source-addresses), lines 168-171. Kernel: KF11, KF12, KF22. Experiments: K8, K13b, K14c.

T16 lists the errnos that make a peer "unreachable now" and declares them "never a configuration mistake". K8 and the source give a different table:

| Cause | Errno, both families | T16 |
|---|---|---|
| no route | `ENETUNREACH` | listed |
| `unreachable` route | `EHOSTUNREACH` | listed |
| `prohibit` route | `EACCES` | listed |
| `blackhole` route | `EINVAL` | **missing** |
| `throw` route with nothing after it | `ENETUNREACH` (the `EAGAIN` of `fib_rules.c:328` never reaches user space) | — |
| no usable source address in the socket's L3 domain, whatever the routes | `EADDRNOTAVAIL`, raised before the route is consulted (K13b with IPv6 disabled, K14c in a VRF) | listed with another meaning |
| link-local peer, no scope id, unbound socket | `EINVAL`, and permanent | listed as transient |
| a connect from an IPv4-mapped peer to an IPv6 peer without a disconnect | `EAFNOSUPPORT` | missing (N05) |

An implementation following T16 literally treats `EINVAL` as something other than "retry later", which turns an operator's blackhole route for a peer into a hard failure. A link-local literal without a scope on an unbound tunnel can never connect, so "never a configuration mistake" is false for it. And a link-local peer *with* a scope rebinds the socket to the scope device (`datagram.c:228`): on an unbound tunnel the socket becomes device-bound by the connect (K8: `bound_dev_if=0` before, `11` after, `0` again after the disconnect), and on a VRF-bound tunnel the VRF binding is **replaced** by the member device's (K8: `6` → `7`), which T11/T21's model of "the kernel binding" does not foresee and which G5 ("never sends through another device") cannot distinguish from a leak.

**Resolution:** Replace T16's parenthetical with a table that classifies every errno a connect can return, including `EINVAL` (transient when a blackhole route exists, permanent for an unscoped link-local peer) and `EAFNOSUPPORT` (defect). Define the grammar for zone-qualified literals (`fe80::1%eth0`), require a bind device or a zone for link-local peers at load time, and state that connecting to a scoped link-local peer sets the socket's binding to that device and what the daemon does about it on a VRF-bound tunnel. Say that `EADDRNOTAVAIL` means "no source address", which no route can fix.

**Validation:** K8 (`k_probe.sh`), K13b (`k_reconn.sh`), K14c (`k_ll.sh`).

### N08 — The null device's IPv6 link-local address is assumed, not ensured

**Severity: Medium. Type: Unstated host dependency; kernel-confirmed.**

**Evidence:** [H2](../docs/spec/hosts.md#address-families), lines 14-20 ("the null device, which gets a link-local address and so a source"); [D7](../docs/spec/discard.md#the-null-device), lines 57-62; [D13](../docs/spec/discard.md#leaving-the-discard-address), lines 99-103; [D2](../docs/spec/discard.md#addresses), lines 18-23 ("no source address of the family at all"); [H7](../docs/spec/hosts.md#vrfs), lines 46-53. Kernel: KF17, KF20, KF22, KF23. Experiments: K5, K14b, K14c, K14d.

A dummy gets a link-local address by default (K5), but only by addrconf, which the host controls: `net.ipv6.conf.default.addr_gen_mode=1` (none), the same on the device, or `disable_ipv6` on `default` leave it without one. K14b, with `addr_gen_mode=none` and no other IPv6 address on the host, shows what then happens outside a VRF: the connect to `100::` **succeeds with source `::1`**, the kernel's last resort. Inside a VRF (K14c) it fails `EADDRNOTAVAIL`, because `::1` is not in the VRF domain; adding `fe80::1/64` to a VRF member makes it succeed with that source; adding it to the null device and enslaving the null device to the VRF does not, because enslaving cycles the device and the cycle removes the address (`vrf.c:1084-1096`, KF20). IPv4 needs nothing: a connect with no IPv4 address anywhere succeeds with source `0.0.0.0`, also when VRF-bound (K14d).

The specification therefore gets the IPv6 discard connection "for free" only on hosts that generate link-local addresses, and D2's fallback to the IPv4 discard address kicks in on exactly the hosts where N09 would rather keep IPv6. The maintainer's note during this audit ("account for cases where v6 LL is not assigned automatically for dummies, setting `fe80::1/64` for the dummy interface at least when needed") is the right remedy, with two qualifications the kernel imposes: the address must be re-added after any VRF enslavement of the device, and for a VRF-bound tunnel the address only helps if the null device is a member of that VRF (or an address exists on another member), because source selection stays inside the VRF domain (KF22, `ip6_route.h:141-147`).

**Resolution:** D7: after creating the null device the daemon checks for a link-local address and, if none appears, assigns `fe80::1/64` (the address is local to the device, the device never transmits, and `IFF_NOARP` skips duplicate address detection); the check is repeated after the device is enslaved or cycled. H2/H7: state the source the discard connection will use (the null device's link-local outside a VRF, a VRF member's address inside one) and that `::1` may be selected when the host has nothing else. D2: the fallback to the other family's discard address is for `AF_INET` sockets and `disable_ipv6` hosts, not for a missing link-local address. Or adopt N03 and need no source at all.

**Validation:** K14b–K14d (`k_ll.sh`).

<a id="n09"></a>

### N09 — The IPv6 discard address is the better sink wherever IPv6 is enabled

**Severity: Medium (design). Type: Weaker choice than the kernel allows.**

**Evidence:** [D2](../docs/spec/discard.md#addresses), lines 18-23 ("A tunnel goes to the discard address of its family"); [D1](../docs/spec/discard.md#addresses), lines 12-16; [H2–H5](../docs/spec/hosts.md#address-families); [T4](../docs/spec/tunnels.md#address-families). Kernel: KF7, KF8, KF10, KF22. Experiments: K2b, K3, K7, K13b, K14d.

The maintainer suggested during this audit that IPv6 discard routes be used where possible. The kernel evidence supports it on every count the specification cares about: IPv6 route removals on device down and unregister are notified while IPv4 ones are not (K7, N01); IPv6 has no on-link fallback, so a missing route is a visible `ENETUNREACH` rather than an ARP leak (K3, N06); a tunnel whose `ip_version` is `V4` can sit on `100::` on its `AF_INET6` socket exactly as on `::ffff:192.0.0.8` (K2b: `bind=vrfA connect=100::` and `connect=::ffff:192.0.0.8` both succeed on one socket), and leaving it for an IPv4 peer is the ordinary family change T3 already allows; one null-device route and one grace period replace two. The limits are the ones already measured: `AF_INET` sockets (T4; `ipv6.disable=1`) have no IPv6; with `disable_ipv6=1` the route cannot be installed (`EACCES`, K13b) and the connect fails `EADDRNOTAVAIL`; and N08's link-local condition must hold. `bindv6only` does not matter for a native IPv6 destination (K1's last run).

**Resolution:** D2 becomes: a tunnel on an `AF_INET6` socket goes to `100::` whenever an IPv6 route to it exists or can be installed; `192.0.0.8` is used on `AF_INET` sockets and on hosts where IPv6 is disabled by sysctl, detected by the route installation's `EACCES` or the connect's `EADDRNOTAVAIL`, not by the tunnel's family. H2 and H3 change accordingly. This is moot under N03.

**Validation:** K2b, K13b, K14 as above; a daemon run on an IPv4-only configuration with the change.

### N10 — Module autoload is not disabled in user namespaces

**Severity: Low. Type: Factual error.**

**Evidence:** [H9](../docs/spec/hosts.md#containers-and-namespaces), lines 66-72 ("In a user namespace the kernel autoloads no module; the modules are the host's to load"); [R1](../docs/spec/requirements.md#the-host), line 17; [G10](../docs/spec/promises.md#unconditional-promises), line 24. Kernel: KF21.

None of the autoload paths the daemon's objects depend on checks a namespace or a capability (`rtnetlink.c:3849-3855`, `af_inet6.c:164-173`, `genetlink.c:1446-1447`, `l2tp_netlink.c:620-626`). On the host of this audit, `ip link add ... type nlmon` inside a Docker container with `NET_ADMIN` loaded `nlmon`, and `unshare -Urn ip link add ... type ifb` as the unprivileged user loaded `ifb`. H9's sentence is false; what is true is that distributions may restrict autoload (`kernel.modules_disabled`, a modprobe policy), which is a host matter R1 should name.

**Resolution:** Delete the sentence; say that autoload is the kernel's and may be restricted by host policy, in which case R1's "loaded" applies.

### N11 — Taking a device down removes IPv6 addresses only when `keep_addr_on_down` is off

**Severity: Low. Type: Overstated kernel fact.**

**Evidence:** [S12](../docs/spec/sessions.md#hardware-addresses), lines 88-98; [G4](../docs/spec/promises.md#unconditional-promises), line 18. Kernel: KF20. Experiment: K14.

<a id="n12"></a>

### N12 — The event monitor's filter also drops the replies to the monitor's own requests

**Severity: Low. Type: Missing constraint.**

**Evidence:** [A5](../docs/spec/architecture.md#layers), lines 62-71 ("Event monitor: one subscription ... filtered in the kernel"; "rtnetlink requests: ... dump for resync"); [E20](../docs/spec/events.md#monitor-loss), lines 128-137 ("reopens it, seeds it from the kernel"); [A18](../docs/spec/architecture.md#why-this-shape). Kernel: KF15. Experiment: K10c.

A classic BPF filter attached to a netlink socket is applied to unicast replies (`af_netlink.c:1347-1352`) and to dump replies (`2278-2281`) as well as to broadcasts. K10c: with a filter that returns 0, a `RTM_GETLINK` request on the same socket gets no reply (timeout); with a filter that accepts, it does. A filter that passes only link, address and discard-route removals would therefore silently eat a route dump used for seeding on that socket.

**Resolution:** State that requests and dumps are never sent on the filtered socket, or that the filter passes replies to the socket's own port (the port is in the header the filter can read).

### N13 — Session deletion is synchronous on 6.8 and asynchronous from 6.11 on

**Severity: Low. Type: Unstated kernel-version dependency.**

**Evidence:** [T8](../docs/spec/tunnels.md#creation-and-identifiers), lines 63-68; [T24](../docs/spec/tunnels.md#changes-applied-in-place), lines 185-187; [S15](../docs/spec/sessions.md#cookies), lines 112-114 ("once the old one is gone"); [S27](../docs/spec/sessions.md#external-deletion), lines 194-201; [T25](../docs/spec/tunnels.md#identifier-conflicts). Kernel: KF3, KF4. Experiments: K18, K24.

On 6.8 a session deleted through netlink is unhashed and its device unregistered before the netlink call returns (`l2tp_core.c:1584-1596`, `l2tp_eth.c:157-175`): K18 re-created the same session id under a new name immediately, three times out of three. From 6.11 on (`v7.0 l2tp_core.c:1733-1740`) the deletion is queued, so the same sequence can be refused `EEXIST` for a moment, as `docs/testing.md` line 98-99 already observed on some run. Tunnel deletion is queued on every kernel (K24: six of ten immediate re-creations refused). T8 states the wait for tunnels only; S15 and T24 say "once the old one is gone" for sessions without a mechanism; T25's retries absorb both, which should be said. S27's proof ("the observed removal of its device followed by the kernel reporting no session") holds on 6.8 because the `RTM_DELLINK` precedes the netlink acknowledgement; on newer kernels the order is not guaranteed.

**Resolution:** State that both deletions may be asynchronous depending on the kernel, that re-creation after either is retried as a transient conflict, and that the daemon never assumes the order of the link notification and the netlink reply.

### N14 — The kernel's tunnel record keeps the previous IPv6 peer after a disconnect

**Severity: Low. Type: Incorrect observability claim.**

**Evidence:** [O9](../docs/spec/observability.md#state-visible-on-the-host), lines 51-56 ("with the current peer (a discard address while there is none)"); [T20](../docs/spec/tunnels.md#source-addresses). Kernel: KF24. Experiment: K15a.

After `connect(AF_UNSPEC)` the kernel's tunnel record reported `IP6_SADDR = ::` and `IP6_DADDR = ::ffff:10.1.1.9`, the peer before the disconnect: `__udp_disconnect` clears the IPv4 destination and the sources but not `sk_v6_daddr` (`udp.c:2006-2011`), and the tunnel dump reports `sk_v6_daddr` for `AF_INET6` sockets (`l2tp_netlink.c:337`). For a tunnel in T20's disconnected state, and for every tunnel under N03, `ip l2tp show tunnel` shows the last peer with an empty source.

**Resolution:** O9: a disconnected tunnel is recognisable by the empty source, and the peer shown is the last one connected to.

### N15 — `docs/testing.md` repeats E21's timeout claim

**Severity: Low. Type: Documentation error (companion of F35).**

**Evidence:** [`docs/testing.md`](../docs/testing.md) lines 100-101; [E21](../docs/spec/events.md#monitor-loss). Experiment: K10.

"A netlink socket whose receive queue is full loses unicast replies too: a lookup on an overflowed subscription times out rather than failing" is what the daemon's tests observed; K10 shows the kernel's contract is `ENOBUFS` on the next receive unless `NETLINK_NO_ENOBUFS` is set, with the reply lost in both cases and the acknowledgement possibly delivered without it. The pitfall list should say so, because a test written to expect a timeout passes or fails depending on a socket option.

### N16 — The receive-buffer request is capped by a limit the daemon's capability can bypass

**Severity: Low. Type: Unstated choice.**

**Evidence:** [R10](../docs/spec/requirements.md#the-host), line 26 ("whatever `net.core.rmem_max` allows granted"); [E20](../docs/spec/events.md#monitor-loss), lines 128-130; [G10](../docs/spec/promises.md#unconditional-promises). Kernel: `net/core/sock.c:1271-1275`.

`SO_RCVBUF` is capped by `rmem_max`; `SO_RCVBUFFORCE` is not and needs `CAP_NET_ADMIN`, which the daemon has. Neither changes a global setting, so G10 does not forbid it. K10 also shows the kernel doubles the requested value (4096 requested, 8192 granted), which E20's "granted as the host allows" should mention when the number matters for a resync budget.

**Resolution:** Say whether the cap is accepted on purpose; if the 8 MiB matter, use the force variant and say so.

### N17 — The cookie grammar is a project policy stricter than the kernel's

**Severity: Low. Type: Unstated policy.**

**Evidence:** [C8](../docs/spec/configuration.md#session-entries), lines 64-65; [S14](../docs/spec/sessions.md#cookies). Kernel: KF25.

The kernel accepts a cookie of any length up to 8 bytes (`l2tp_netlink.c:584-600`, policy `913-920`); C8's 8 or 16 hexadecimal digits are RFC 3931's lengths and a choice. K11 confirms the semantics C8 and S14 state (a frame with the configured `peer_cookie` is delivered, one without or with the tunnel's own `cookie` is dropped, also with a 4-byte cookie and with the default layer-2 sublayer).

### N18 — The daemon must run on non-systemd, non-GNU Linux hosts with only `/proc` and `/sys` mounted

**Severity: Medium. Type: Missing requirement; systemd and glibc assumptions in the text.**

**Evidence:** [R12](../docs/spec/requirements.md#the-host), line 28 ("An init system that treats the parent's exit as readiness ... With systemd, the supplied unit"); [R7](../docs/spec/requirements.md#the-host), line 23; [R16](../docs/spec/requirements.md#the-operator), line 40 ("the host's resolver"); [P21](../docs/spec/process.md#the-supplied-systemd-unit), lines 141-149 (the only process-integration section, written as MUSTs); [A1](../docs/spec/architecture.md#layers), lines 37-42 ("the installer"); [L1](../docs/spec/library.md#boundaries); F32; N04.

The maintainer's requirement, stated during the audit: "this daemon must work on non-systemd or non-GNU Linux-based systems where `/proc` and `/sys` are mounted; do not expect freedesktop.org layout or anything." Nothing in the specification contradicts it, but the text never states it, and three places lean the other way: P21 is the only description of how the process is integrated and is phrased as a requirement on "the unit"; R16 and F32 reason about "the host's resolver" in terms of NSS and systemd-resolved, which do not exist on a musl host; and this audit's own alternative under N04 (a `sysctl.d` fragment ordered after `systemd-sysctl.service`) is a systemd mechanism. The daemon already runs in exactly such an environment, since the repository's container tests execute a musl build under `alpine` without an init system, so the gap is in the contract, not the code.

**Resolution:** Add to the host requirements: a Linux kernel with the L2TP support of R1, `/proc` and `/sys` mounted, any init system and any libc; and name the process contract as the normative interface, of which the systemd unit is one integration: the daemon double-forks and its parent exits 0 at readiness (P4, P6), it publishes a PID file at a configurable path (P10), it takes `SIGHUP`, `SIGTERM` and `SIGINT` (P12), it logs to standard error (O1), it reads its files from the documented `/etc` paths (C1), and it needs nothing else from the host: no `/run/systemd`, no `sd_notify`, no journal, no D-Bus, no `sysctl.d`, no `tmpfiles.d`, no XDG or freedesktop path, and no installer (A1's installer is a convenience, not a prerequisite). State what `/sys` is used for, if anything; the specification mentions only `/proc` (R7). Scope P21 to "when the supplied unit is used" and keep its hardening clauses there. Define "the host's resolver" (R16, T14, E10–E11) as the libc resolver of the build: on musl `/etc/resolv.conf` and `/etc/hosts` with no NSS, so F32's nss-resolve concern applies to glibc builds only, while answer ordering, timeouts and search-domain behaviour differ between the two libcs and the answer-selection rules of T14/T15 must not depend on them. Under N04, the daemon-side option is the portable mechanism for `bindv6only`; the `sysctl.d` fragment is an alternative only where systemd exists.

**Validation:** Start the daemon from a plain `sh` entrypoint in the audit's `alpine` container (musl, no init), with a configuration of one tunnel and one session, and check readiness by the parent's exit status and the PID file alone; the existing `tests/docker` matrix already exercises the musl build this way and can carry the check.

<a id="n19"></a>

### N19 — Configurable resolvers (`resolvers.<name>`) are coming; the DNS rules must be rewritten around them

**Severity: Low (forward-looking). Type: Announced configuration change the specification must absorb.**

**Evidence:** [C5](../docs/spec/configuration.md#documents), lines 30-36 (a document has two tables); [C7](../docs/spec/configuration.md#tunnel-entries), lines 45-53; [T14–T15](../docs/spec/tunnels.md#peers), lines 106-123; [E10–E11](../docs/spec/events.md#dns-events), lines 76-88; [A5](../docs/spec/architecture.md#layers), line 71 ("Resolver: the host's resolver, in the background, one task per configured host name"); [A9](../docs/spec/architecture.md#concurrency), lines 95-97; [R16](../docs/spec/requirements.md#the-operator), line 40; [G10](../docs/spec/promises.md#unconditional-promises), line 24; F17; F32; N18. Kernel: KF26, KF27.

The maintainer announced during the audit that the `iphost` crate will gain explicit resolver and bind-interface knobs: a configuration gains a `resolvers` table (plural, like `tunnels` and `sessions`; the maintainer corrected the first spelling `resolver.<name>` to `resolvers.<name>` for consistency) whose entries name a resolver by address or by a discovery method (DHCPv6 Information-Request, or router advertisements) and optionally a bind interface, and a tunnel either names one of the configured resolvers or uses the system resolver. The specification currently has no resolver object at all: A5 and R16 speak of "the host's resolver", T14/T15/E10/E11 of "answers" without saying who asks, and F17 already found the selection and freshness rules underspecified. The change therefore touches:

- **Configuration.** C5's "two optional tables" becomes three (`tunnels`, `sessions`, `resolvers`); C7 gains an optional key, presumably `resolver_name` by the convention of `tunnel_name`, whose value must name a `resolvers.<name>` entry of the merged configuration (an unknown name is a hard mistake under C10/C12, like an unknown `tunnel_name`); merge semantics (C2) and uniqueness checks (C9) extend to the new table; `--check` output (O8) renders it.
- **Semantics of answers.** T14's "first usable answer of that family" and T15's refresh and retention rules must be stated per resolver, including which resolver a tunnel without the key uses (the libc resolver of the build, N18), what "system resolver setting" means on musl and glibc, and how a resolver entry's own change on reload (address, method, bind interface) re-resolves every tunnel that names it without re-creating anything (G3).
- **Discovery methods and the kernel.** For router advertisements the kernel already does the work: RDNSS and DNSSL options are forwarded to user space on `RTNLGRP_ND_USEROPT` (KF26), a group the existing rtnetlink monitor can join, so no raw ICMPv6 socket and no capability beyond what the daemon has are needed; the specification should say that this is the mechanism, that the answers carry the advertising interface and lifetimes, and that the monitor's filter (N12) must pass these messages. For DHCPv6 Information-Request the daemon must send to `ff02::1:2` from a UDP socket bound to port 546 on the interface, which needs `CAP_NET_BIND_SERVICE` or a lowered `ip_unprivileged_port_start` (KF27): G10's capability list must then grow or the method be documented as needing the capability.
- **Binding.** A resolver's bind interface is a device binding of the daemon's DNS socket and follows the same rules as a tunnel's (T10–T12, F01 corrected: no capability for a first bind, a disconnect before a rebind); a resolver bound to a VRF queries through the VRF's table (KF8). A resolver whose device is absent gives no answers, and the tunnels that name it stay pending without affecting readiness (P7), which should be said.
- **Events and loss.** E10/E11's "a failed resolution keeps the previous answer" must be stated per resolver; a resolver learned from RAs whose lifetime expires, or whose advertising router disappears, is a new event the events page must cover; the monitor-loss resync (E20) must include re-reading the user options.
- **Process.** Under systemd, the unit's socket-family restriction (F32) is satisfied by a built-in resolver that uses only `AF_INET`/`AF_INET6` UDP; the system-resolver path keeps F32's concern on glibc hosts.

Where the mechanism lives is undecided: the maintainer added that if updating `iphost` is out of scope or too much, a minimal alternative may be implemented in rs-l2tpd itself. The specification work above is the same either way, because it describes the configuration and the behaviour, not the crate. The kernel facts also say what "minimal" can be: a resolver given by address with an optional bind interface needs one bound UDP socket per resolver and nothing else; RA-based discovery needs only the netlink monitor joining `RTNLGRP_ND_USEROPT` (KF26); DHCPv6 Information-Request is the costly method (a client state machine, port 546 and the capability of KF27) and could be the one left to `iphost` or omitted at first. The specification should name which methods are in scope at each stage so that the lenient conversion (C10/C12) can reject a method that is not implemented as a hard mistake rather than accept it silently.

**Resolution:** When the change lands, in whichever crate, add a resolver page or section with the object model (named resolvers, methods, binding, lifetimes), rewrite T14/T15/E10/E11 and A5/A9 around it, extend C5/C7/C9/O8, name KF26 as the RA mechanism and the capability consequence of KF27, and fold F17's open questions into the new text. Until then the specification should at least say that "the host's resolver" means the libc resolver of the build (N18).

**Validation:** Configuration test vectors for the new table and key (merge, unknown name, uniqueness); a container with a router advertising RDNSS (`radvd` or a hand-built RA) and the daemon's monitor subscribed to `RTNLGRP_ND_USEROPT`; a DHCPv6 server in a second namespace for the Information-Request path, with and without the capability.

## Decision: unconnected sockets, and the kernel requirements it rests on

The maintainer decided, after N03 and K15: "if non-connected sockets can be used for kernel tunnels, we should use such ones where applicable, instead of doing hacks with routes. If this stands for every ≥ 6.8 non-strangely-configured kernel build and sysctl combination, we can drop discard route and dummy interface (hence its monitoring too) entirely, iff connecting such sockets later remains possible." Two further instructions came with it: "we must state which kernel feature/configuration we require, precisely", and "requirements should be minimal and conditional on features where applicable". Both conditions of the decision were then checked.

**Condition 1, every kernel ≥ 6.8.** The property has two halves, and neither depends on a configuration option or a sysctl. Registration: `l2tp_validate_socket` checks the socket's namespace, type (`SOCK_DGRAM`), family (`AF_INET`/`AF_INET6`), protocol (`IPPROTO_L2TP` for IP encapsulation) and that it is not already a tunnel socket, and nothing else; `l2tp_tunnel_register` adds no state check. Sink: `l2tp_xmit_core` drops every frame when `tunnel->fd >= 0 && sk->sk_state != TCP_ESTABLISHED`. Both were checked in `net/l2tp/l2tp_core.c` of every release tag from v6.8 to v7.3 (v6.8, v6.9, v6.10, v6.11, v6.12, v6.13, v6.14, v6.15, v6.16, v6.17, v6.18, v6.19, v7.0, v7.1, v7.2, v7.3): zero state checks in registration in all sixteen, the transmit check present in all sixteen; the Ubuntu 6.8.12 tree and mainline `d135ab4` agree. The sysctls that matter to this daemon (`bindv6only`, `disable_ipv6`, `keep_addr_on_down`, `addr_gen_mode`) act on address selection and on later connects, never on registration or on the transmit check. What would count as "strangely configured" is a kernel without `CONFIG_L2TP_IP` or `CONFIG_L2TP_ETH`, which cannot run the daemon at all, or a security module that denies `connect` to this process, which is a host policy outside the kernel's L2TP contract.

**Condition 2, connecting later.** K16, end to end against a peer in another namespace: a tunnel and session created on an unconnected `AF_INET6` socket; the peer's frames were delivered to our session device while our socket was still unconnected (receive is demultiplexed by session id, KF1); after a `connect` our frames reached the peer's session device; after a disconnect they were dropped again; after a reconnect they reached the peer again. The same with the socket bound to a device before the tunnel was created (the binding survived, frames delivered), with an IPv6 outer address, and with an `AF_INET` socket.

Both conditions hold. **The decision stands**, and with it: the discard addresses (D1–D6, D13), the null device (D7–D10, R2, R19's `rsl2tpnull*`, R33), route installation and repair (D8, D11–D12, E9, E15, E16, R32, H8), the ten-second grace in G15, the route multicast groups and the route part of the monitor's filter (A18), and the findings N01, N02, N06, N08, N09, F05, F06, F14 and F15 become moot for the specification. What remains from this family: N14 (the kernel record of a disconnected tunnel shows the last peer and an empty source), the fact that a tunnel receives while unconnected (which the discard variant shared), and T20's "disconnected" state, which becomes the state of every tunnel without a reachable peer.

## What the kernel evidence suggests

These are the resolutions the facts above support, in the order of their effect. Item 1 is now decided; the rest are options for the specification, not implementation instructions.

1. **Make "disconnected" the state of a tunnel without a reachable peer (N03). Decided, see above.** The kernel creates the tunnel and its sessions on a bound, unconnected socket and drops every frame itself, on every tested kernel, for both families, bound or not. This removes the discard addresses, the null device, the grace period, route installation and repair, and with them N01, N02, N06, N08, N09 and the kernel-dependent parts of F05, F06, F14, F15 and F16. Readiness keeps its meaning (the objects exist). G5 holds without conditions. `CAP_NET_RAW` is not needed for the first bind (KF6), and the bind is never changed in place if every reconnect disconnects first. What changes visibly: `ip l2tp show tunnel` shows an empty source and the last peer (N14), and the one-second pending-peer retry becomes the only path out of the state.
2. **If discard addresses stay, close the four holes with the events the kernel does send.** Link events for owned null devices and configured VRF names (N01); route additions and replacements for the discard prefixes, or binding discard-connected tunnels to the null device (N02); never connecting a device-bound tunnel to a discard address (N06); `100::` wherever IPv6 is enabled, with `fe80::1/64` assigned when no link-local appears and re-assigned after enslavement (N08, N09).
3. **State the two socket rules.** `IPV6_V6ONLY` is immutable on L2TP/IPv6 sockets: require `bindv6only=0` (checked at start-up; established by the daemon in its own namespace under a configuration option, the decided mechanism for namespace-changing exceptional operations, which may default to on because it acts only on a value of 1 that would otherwise disable every IPv4 peer silently, with G10 and the unit amended for that case), and in every case detect the value with `getsockopt` on each new socket and give IPv4 peers `AF_INET` sockets when it is set (N04). Every peer change is disconnect, rebind, connect (N05); the source read back from the socket is trusted only after that sequence.
4. **Use the kernel's atomic operations where the specification builds races by hand.** `SO_BINDTOIFINDEX` binds to the index the name resolved to, so T10's before-and-after name verification is unnecessary (KF6; F01 corrected). `L2TP_ATTR_IFNAME` deletes or queries a session by its creation-time name in one kernel call (KF2), which shortens F02's window between proof and deletion, without closing it.
5. **Say what the data path does not check.** F36 is now reproduced: with the tunnel's local device inside a VRF, a frame from another namespace through another device with a non-peer source reached the session device (K11), and only cookies stopped it. The specification should name cookies as the only admission control the daemon can offer, and external packet filtering as the rest.

## Kernel versions

The facts table marks what holds in all three trees. The differences between the Ubuntu 6.8 tree and v7.0 that the specification should know are: tunnels and sessions live in per-namespace IDRs and `l2tp_v3_session_get` replaces the hash lookup (KF1, KF5); session deletion is queued (KF4, N13); the l2tpeth device sets `lltx` instead of `NETIF_F_LLTX` (no behavioural change). Between v7.0 and mainline, `net/l2tp` changed only in a refcount check of the by-name lookup, `send_seq` accessors and per-namespace generic-netlink multicasts. Every behaviour this audit relies on (demultiplexing by session id, the stored interface name and its lookup, asynchronous tunnel deletion, the transmit check on unconnected sockets, the bind capability rule, the on-link rule, the silent IPv4 route flush, the disconnect semantics, the netlink overflow behaviour, the dummy and l2tpeth device properties) is present unchanged in all three.
